第一章：AI 核心概念与技术体系

建议时长：12 分钟

这一章非常重要，因为你希望员工不仅会聊天式地使用 AI，还能够理解其技术体系，为后续建设打下基础。

1.1 大语言模型与 AI Agent

首先介绍几个基础概念。

概念	英文	重点讲解
大语言模型	LLM	AI 的基础能力来源
提示词	Prompt	如何向 AI 描述任务、要求和约束
上下文	Context	AI 当前能够参考的信息
上下文窗口	Context Window	AI 一次能够处理的信息容量
AI 智能体	AI Agent	能够规划任务、调用工具和执行多步骤操作的 AI 系统
工具调用	Tool Calling	AI 如何使用外部工具
幻觉	Hallucination	AI 为什么可能生成错误但看似合理的答案

这一部分不需要深入模型训练原理。

需要重点区分两个概念：

传统 AI 对话：

用户提出问题 → AI 给出回答。

Agent 工作模式：

用户提出目标 → AI 分析任务 → 调用工具 → 执行操作 → 检查结果 → 继续执行。

这两种工作模式的差异，会直接影响后面所有案例。

1.2 Skill：把经验转变为可复用能力

这是你非常重视的核心概念。

建议讲清楚以下内容：

* Skill 是什么？
* Skill 与 Prompt 有什么区别？
* Skill 与 Agent 有什么关系？
* 什么样的工作流程适合沉淀为 Skill？
* 如何创建、维护和共享 Skill？

这里需要建立一个重要认知：

Skill 不只是一个提示词，而是将特定任务的方法、操作步骤、规则及相关资源组织为可复用能力的一种方式。

例如，季华驱界未来可以建设：

* 技术论文分析 Skill
* 嵌入式代码审查 Skill
* 测试日志分析 Skill
* 技术周报生成 Skill
* 产品宣传材料生成 Skill

当然，Skill 的具体组织形式和运行能力取决于所使用的平台，不能认为定义一个 Skill 就能自动完成所有工作。

1.3 MCP：连接 AI 与外部系统

MCP（Model Context Protocol）。

重点解释：

* MCP 是什么？
* MCP Server 和 MCP Client 的关系。
* MCP 与 API 的区别。
* MCP 与 Skill 的区别。
* MCP 如何让 AI 获取外部数据并使用工具？

建议用一个非常直观的例子：

假设研发人员需要分析机器人的运行日志。

没有 MCP：

研发人员手动导出日志，再复制给 AI 分析。

有 MCP：

AI 在授权范围内，通过 MCP 工具获取日志，并协助完成分析。

这里可以引出企业内部系统集成。

例如：

GitHub / GitLab、知识库、测试平台、日志系统等，都可能成为 AI 可以访问的工具或数据来源。

但需要强调：MCP 提供连接协议，不会自动解决权限控制、数据安全和操作审批问题。

1.4 AI 的能力边界与人机协作

这一部分是之前你特别强调的内容。

建议明确介绍：

Human-in-the-Loop（人在回路）

即在 AI 工作流程中，为需要人工判断或批准的关键步骤设置人工参与机制。

以研发为例：

工作阶段	AI 的职责	人工职责
需求分析	梳理需求、发现遗漏	确认需求是否合理
技术调研	检索文献、比较方案	核实来源与技术可行性
技术设计	提出方案、分析风险	决定技术路线
代码开发	生成和修改代码	审查关键实现
自动化测试	编写测试、分析结果	确认测试覆盖与有效性
真机调试	分析日志、辅助定位问题	操作设备、判断安全性
发布部署	生成发布计划、辅助检查	审批并控制发布

尤其是电机驱动、力矩控制和机器人运动控制等涉及物理安全的系统，不能将 AI 生成的代码直接视为已经通过工程验证。

本章希望员工最终形成的认知：

AI 可以参与大量工作，但 AI 的执行能力不等于技术决策权，更不等于最终责任。

你之前特别提到，希望照顾公司管理者对工作流程记录、工作汇报的需求。

主要介绍以下几个方面。

场景	AI 的应用

2.2 重点演示案例：生成企业宣传 PPT

这个案例比较适合现场展示，因为效果直观，而且全体员工都能理解。

建议演示的过程：

第一步：收集资料

收集企业官网、产品介绍、技术参数等公开资料。

* 目标客户。
* 行业应用。

第三步：生成 PPT

根据不同受众，形成不同版本：

* 客户介绍版本。
* 投资人介绍版本。

第四步：人工 Review

重点核对公司介绍、产品参数和技术优势，避免 AI 编造数据。

将 PPT 制作过程沉淀为“企业产品宣传 Skill”。

以后新增产品，只需要更新产品资料，就可以按照统一的结构、品牌规范生成宣传材料。

这一部分也能呼应第一章所讲的 Skill。

第三章：AI 赋能调查研究与技术创新

建议时长：12 分钟

这一章主要面向研发人员，同时也适合管理层了解 AI 如何辅助企业技术决策。

它与你同学公司的实际业务高度相关。

3.1 AI 辅助专业研究

介绍 AI 在以下场景中的应用：

研究方向	应用
行业研究	机器人产业发展、市场趋势
竞品分析	国内外关节模组与伺服驱动器对比
论文研究	检索、阅读、理解学术论文
技术趋势	新型执行器、控制算法和材料技术
专利研究	检索相关专利、分析技术路线
技术可行性	对比不同技术方案的原理与局限

重点不是让 AI 简单地“总结一篇论文”。

而是让员工理解如何将 AI 作为研究助手（Research Assistant），逐步完成专业技术调查。

3.2 重点案例：机器人关节模组技术优化研究

我们之前讨论过两个方向：

方向 A：提高关节模组的力矩密度

Torque Density

通过研究相关论文和竞品，探索：

* 电机设计。
* 减速机构。
* 散热设计。
* 材料及结构优化。
* 控制系统与硬件协同优化。

这个方向适合机械、电机和硬件工程师。

方向 B：提升机器人关节的动态力矩控制能力

研究机器人在受到外部作用力变化时，如何实现合适的动态响应。

可以涉及：

* 阻抗控制（Impedance Control）。
* 导纳控制（Admittance Control）。
* 力矩控制（Torque Control）。
* 扰动观测器（Disturbance Observer）。
* 力矩估计与反馈控制。

这个方向更适合软件、嵌入式及算法工程师。

需要注意，这些方案的适用性取决于关节模组的传感器、驱动器、控制架构等实际条件。

我的建议

第三章选择方向 B 作为主要案例。

原因是它可以自然衔接到第四章的代码开发。

我们可以用同一个技术主题展示完整的工作过程：

论文研究 → 技术分析 → 需求定义 → 代码开发 → 测试验证 → 真机调试。

这样的课程连续性会明显优于三个互不相关的演示。

3.3 研究过程中必须掌握的方法

这里需要强调三件事。

第一，来源可追溯。

AI 提到的论文、算法、技术参数必须能够找到真实来源。

第二，区分事实与推断。

论文已经验证的结论，不等于一定适用于季华驱界的产品。

第三，对照具体工程约束。

不能只讨论理论优势，还要考虑算力、实时性、控制频率、硬件成本、温升、稳定性等实际限制。

第四章：AI 赋能软件研发与代码管理

建议时长：21 分钟

这是整场培训中技术深度最高的一章。

因为公司有超过 20 名研发人员，我建议将这一章作为重点。

4.1 AI 辅助软件开发的工作模式

先简要介绍 AI 编程的发展方式。

从早期的：

代码补全 → 对话生成代码

到现在的：

Agent 驱动的多步骤软件开发

让大家理解，AI 编程工具已经不只是生成一段函数，而是能够在授权范围内读取仓库、分析依赖、修改文件、执行命令与测试。

可以介绍几个代表性工具，例如：

* Codex
* Claude Code
* Cursor

这一部分不需要做工具排名，而是解释它们如何参与开发流程。

4.2 规范驱动开发：Spec-Driven Development

这是你特别希望介绍的重点。

建议使用更规范的名称：

规范驱动开发（Spec-Driven Development，SDD）

OpenSpec 是支持这种工作方式的工具之一。

需要说明：

传统 AI 编程容易出现一个问题：

开发者直接告诉 AI：“帮我实现某个功能。”

AI 立刻开始修改代码。

但可能出现：

* 需求没有定义清楚。
* 技术方案未经评审。
* 影响范围没有分析。
* 缺少明确验收标准。
* 代码与文档不一致。

因此，我们引入规范驱动的开发流程。

4.3 OpenSpec 工作流程

可以用下面这个模型介绍 OpenSpec：

需求提出 → 需求规范 → 技术设计 → 任务拆解 → 代码实现 → 测试验证 → 归档维护

结合 OpenSpec 的实际工作机制，介绍 proposal、specs、design、tasks，以及变更实施和归档等内容。

需要特别强调：

OpenSpec 并不是自动保证代码质量的工具。

它更重要的价值是让研发人员与 AI 围绕明确的需求、设计和任务协作，使变更过程更加可审查、可追踪。

OpenSpec 中的人工 Review 节点

这应该成为第四章的一个重点知识点。

阶段	AI 能做什么	人工 Review 重点
Proposal	分析变更目标和影响	是否值得做、范围是否合理
Specs	编写需求规格和验收场景	行为定义是否正确
Design	设计技术方案	架构、实时性、硬件约束
Tasks	拆解开发任务	任务是否完整、顺序是否合理
Implementation	修改代码、编写测试	关键逻辑、安全性和质量
Verification	执行测试、整理结果	测试证据是否充分
Archive	整理变更记录与规格	是否与实际实现一致

尤其要让研发人员理解：

AI 可以主导大量执行工作，但关键工程决策应当通过人来确认。

4.4 重点演示：机器人关节控制算法优化

延续第三章的论文研究。

假设我们已经取得季华驱界某关节控制模块的源代码。

目标是：

研究一种适合当前产品的控制策略，改善关节在受到外界扰动时的力矩响应表现。

演示流程可以这样安排。

阶段一：理解已有项目

让 AI 分析：

* 项目目录。
* 模块职责。
* 控制算法实现。
* 数据流与控制流程。
* 已有测试。
* 潜在的性能瓶颈。

阶段二：基于研究成果提出改进

把第三章调查得到的技术方案交给 AI。

要求 AI 分析现有实现与论文方案的差异、适用前提和潜在风险。

阶段三：OpenSpec 规范管理

创建一项变更。

包含：

* 优化目标。
* 技术设计。
* 实施任务。
* 验收指标。
* 测试计划。

阶段四：AI 辅助代码开发

让 AI 依据已确认的规范进行修改。

这一部分可以介绍：

* 代码生成与重构。
* 单元测试。
* 静态分析。
* Git 版本控制。
* Code Review。

阶段五：仿真与真机验证

这是机器人研发与普通 Web 开发非常重要的区别。

需要讲解：

* 仿真测试。
* 电机或关节真机测试。
* 控制日志采集。
* 数据分析。
* 异常定位。
* 参数优化。

这里特别适合重新引入 MCP。

例如，通过内部测试系统提供的 MCP 工具，让 AI 获取测试日志、分析控制误差和异常特征。

但真机执行必须遵循设备安全约束和人工确认机制。

阶段六：持续迭代

把测试结果反馈给 AI，重新分析问题，必要时调整 Spec，再进入下一轮开发。

完成后，将有效的技术经验沉淀为：

* 技术文档。
* 测试报告。
* 项目知识库。
* 可复用 Skill。

这样就完成了从研究到工程验证的闭环。

第五章：总结与企业 AI 能力建设

建议时长：5 分钟

这一章主要回答：

对于季华驱界这样的技术研发企业，未来应该怎样系统建设 AI 能力？

建议围绕三个方面展开。

5.1 建立企业知识库

把分散在研发人员个人电脑、聊天记录和项目文件中的知识，逐步沉淀为企业资产。

例如：

* 产品技术文档。
* 软件架构。
* 硬件规格。
* 测试报告。
* 调试经验。
* 技术研究成果。
* 常见问题与解决方案。

同时区分知识库与 Skill 的职责。

知识库负责保存和组织知识，Skill 侧重于复用特定工作方法与流程，两者可以协同使用，但不是同一个概念。

5.2 建立企业 Skill 体系

从高频工作中逐步选择适合标准化的流程。

初期可以先建设三个：

Skill	面向对象	价值
技术论文研究 Skill	研发人员	提高论文调研效率
研发代码审查 Skill	软件工程师	标准化代码审查流程
项目汇报 Skill	全体员工	规范工作记录与汇报

先验证实际效果，再考虑扩展。

5.3 逐步建设 MCP 集成能力

将企业现有系统逐步接入 AI 工作环境。

可以分阶段：

第一阶段：只读访问文档、代码和日志。

第二阶段：允许执行受控的分析与测试工具。

第三阶段：在具备必要权限、审计和审批措施后，支持部分自动化工作流。

对于真实硬件控制、高风险参数修改和生产系统发布，应保留严格的独立安全控制与人工审批。

二、贯穿整场培训的一条技术主线

我建议把三大应用方向连接起来，而不是完全分开讲。

可以围绕季华驱界的机器人关节驱动产品，设计一个贯穿全程的案例。

阶段	演示任务	对应技术
① 日常办公	根据产品资料生成企业介绍 PPT	AI 对话、文档工具、Skill
② 技术研究	调查机器人关节控制技术，阅读专业论文	AI Research、文献检索
③ 需求设计	将研究成果转化为改进需求	OpenSpec
④ 软件研发	分析代码、实现算法优化	AI Agent、Git
⑤ 测试调试	分析运行日志、定位问题	MCP、AI 数据分析
⑥ 知识沉淀	归档研发结论，建设可复用工作流程	Skill、知识库

其中①是独立办公案例，②到⑥形成连续研发案例。

这条主线有一个非常重要的特点：它展示的是 AI 如何参与完整的工作过程，而不是展示几个孤立的 AI 功能。

⸻

三、我建议额外补充的四个专业概念

除了你明确提出的 Skill、MCP、OpenSpec，我认为还有四个概念值得出现在培训中。

概念	中文	为什么要讲
Agent	智能体	理解 AI 从回答问题发展到执行任务
Context Engineering	上下文工程	理解如何向 AI 提供正确的信息、约束和项目背景
RAG	检索增强生成	理解 AI 如何结合企业知识库获取信息
Human-in-the-Loop	人在回路	理解 AI 与人工之间的责任边界

其中，我认为 Context Engineering（上下文工程）尤其重要。

因为在实际研发中，很多时候影响 AI 表现的不只是模型能力，还有：

* AI 是否理解项目。
* 是否有正确的技术文档。
* 是否了解代码架构。
* 是否知道开发规范。
* 是否取得必要的工具访问权限。
* 是否拥有足够且准确的测试反馈。

这可以把上下文工程、Skill、MCP、知识库和 OpenSpec 串成一个相对完整的体系。

⸻

四、关于课程深度，我有三个建议

建议一：少讲 AI 产品，多讲 AI 工作方式

你面对的是一家有二十多名研发人员的技术公司。

相比单纯介绍 ChatGPT、Claude、Cursor 各有什么功能，更值得讲的是：

如何让 AI 参与日常工作，并且让这个过程可复用、可验证、可维护。

工具可以更换，但建立起来的工程方法可以长期保留。

建议二：把人工 Review 作为贯穿课程的核心原则

不要只在 OpenSpec 中讲人工审核。

论文研究需要审核来源。

企业宣传需要审核事实。

代码开发需要审核设计和实现。

硬件调试需要审核安全性和测试证据。

因此，可以设计一张统一的“AI 能力边界与人工 Review”图，贯穿三个场景。

建议三：第一次培训不要追求完整演示所有步骤

60 分钟的时间非常有限。

尤其是机器人控制算法的完整优化，需要真实代码、硬件环境和测试条件，不适合在现场从零完成。

我建议提前准备好论文、示例仓库、Spec 文件和测试日志。

现场选择最能体现价值的环节，例如：

论文技术分析 → OpenSpec 需求设计 → AI 修改代码 → 真实或预先采集的日志分析。

这样既能展示技术深度，也更容易控制培训时间。

六、需要你重点 Review 的三个问题

第一个：第一章是否要更深入？

目前我安排了 12 分钟介绍 AI Agent、Context、Skill、MCP 和 Human-in-the-Loop。

这些概念是整场培训的基础。考虑到研发人员较多，可以适当增加技术深度，但需要控制概念数量。

第二个：第三章和第四章是否采用同一个连续案例？

我比较推荐将“机器人关节控制算法优化”作为贯穿案例。

从专业论文研究开始，经过 OpenSpec 需求设计，最后进入代码实现、测试和真机调试。

这样可以非常清楚地展示从 AI Research 到 AI Coding 的完整方法。

第三个：是否在培训中加入企业 AI 基础设施建设？

比如企业知识库、共享 Skill、内部 MCP Server、代码仓库集成等。

这部分虽然只有 5 分钟，但对一家 30～40 人、研发人员占比较高的公司来说，我认为有必要。

我对这版大纲的整体判断是：五个章节的结构可以保留，重点放在 Skill、MCP、OpenSpec 三项能力，并通过办公、研究、研发三个场景说明如何真正落地。

我们先把这份目录作为 V1 版。你可以逐章提出调整意见，等目录确认后，再设计各章节的技术内容、真实案例、现场演示以及最终 PPT。
